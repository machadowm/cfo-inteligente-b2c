🔴 Bugs Críticos (produção afetada)

BUGProjeção mensal ainda usa fat do turno atual, não fat_bruto acumulado no mês
orchestrator_service.py · formatar_relatorio_fechamento_dre · linha 305

A variável fat é o faturamento bruto do turno fechado. A projeção deveria ser fat_bruto_mes_acumulado + (media_fat_dia × dias_restantes). Como está, se o motorista fechou R$ 200 num dia no fim do mês, a projeção mostra R$ 200 + (histórico × dias), ignorando os R$ 8.000 que ele já faturou este mês.

projecao_mensal = fat + (media_fat_dia * dias_uteis_restantes)
# fat = faturamento DO TURNO, não do mês
# Deveria ser: fat_bruto_mes + (media_fat_dia * dias_uteis_restantes)

Impacto: projeção sempre subestimada; "Faturamento/dia necessário para a meta" inflado.

BUGdeficit_meta também usa fat do turno, não o acumulado mensal
orchestrator_service.py · linha 306

deficit_meta = max(0.0, meta_mensal - fat) — subtrai a meta do faturamento de um turno, não do acumulado do mês. O "faturamento/dia necessário" é completamente equivocado.

BUGFormatação de mensagem quebrada em _excluir_caixa e _criar_caixa
parametros_service.py · linha 1008, 871

Os f-strings aninhados com *{nome}* estão errados — há um asterisco extra que quebra a negrito:

# Linha 1008:
f"🗑  *Caixa  *{nome}*  excluída com sucesso.*\n"
# Deve ser:
f"🗑  *Caixa {nome} excluída com sucesso!* \n"

# Linha 871:
f"✅  *Caixa  *{nome}*  criada!*\n"
# Deve ser:
f"✅  *Caixa {nome} criada!* \n"

Impacto: formatação visível ao motorista quebrada em toda exclusão e criação de caixa.

BUGDouble-close do cliente Redis no shutdown (aclose chamado duas vezes)
main.py · linha 39-42

No lifespan, o teardown faz:

redis_client = await RedisFSMService.get_client()
await redis_client.aclose()

Mas RedisFSMService.get_client() retorna a instância singleton, e o pool já tem max_inactive_connection_lifetime. O aclose direto fecha o socket mas não chama pool.disconnect(). O correto seria chamar RedisFSMService.close_client() que existe e reseta o singleton, ou fechar via await cls._client.connection_pool.disconnect(). Como está, o _client singleton não é resetado para None, mas o socket subjacente foi fechado — uma futura chamada no mesmo processo usaria um socket fechado.

🟠 Riscos Médios

RISCOOnboarding: estado FSM usa | como separador mas o nome do veículo pode conter |
orchestrator_service.py · linhas 560, 571, 598

O estado é serializado como AGUARDANDO_VEICULO|name:João|veiculo:Honda CG|160. Se o motorista digitar um nome com | (raro, mas possível), os split("|") posteriores desalinham todos os campos. Não há sanitização.

RISCORace condition silenciosa: dois fechamentos simultâneos do mesmo turno
turno_service.py · fechar_turno_com_dre

O UPDATE turnos SET status = 'concluido' não usa WHERE status IN ('em_andamento', 'em_pausa'). Se dois requests chegarem em paralelo (ex: debouncing falhar ou reenvio WhatsApp), o segundo UPDATE tenta fechar um turno já concluído, prossegue silenciosamente (nenhum RETURNING verifica se a linha foi atualizada), e gera um segundo lançamento em fechamento_diario — duplicando o snapshot contábil.

# Vulnerável:
await conn.execute("UPDATE public.turnos SET km_final=$1, status='concluido' WHERE id=$2::uuid", ...)
# Seguro:
row = await conn.fetchrow("UPDATE ... WHERE id=$1 AND status != 'concluido' RETURNING id", ...)
if not row: return {"sucesso": False, "tipo_erro": "TURNO_JA_CONCLUIDO"}
RISCOConsulta de lembretes sem isolamento RLS — usa get_connection(), não get_tenant_connection()
reminder_service.py · _processar_pausas_prolongadas, _processar_turnos_zumbi, _processar_vencimentos_despesas

Todas as queries do ReminderService usam get_connection() (sem RLS). Isso é intencional (varredura de todos os motoristas), mas sem WHERE ativo = TRUE na tabela motoristas. Se um motorista for desativado/deletado no futuro, lembretes continuarão sendo enviados para o telefone dele.

RISCOPausa retroativa usa meio_jornada fixo — pode gerar inicio_pausa > fim_pausa
orchestrator_service.py · linha 1222-1228

A pausa retroativa é posicionada no meio da jornada com meio_jornada + timedelta(minutes=minutos_declarados). Se a pausa for maior que a metade restante (ex: jornada de 3h, pausa de 2h30), fim_pausa pode ultrapassar datetime.now(). O clamp existente (linha 1212) limita os minutos a duração - 5, mas não garante que meio_jornada + duração <= now().

RISCOFallback do odômetro via argumento de comparação na recalibração Full-to-Full é duplamente contado
transacao_service.py · _recalibrar_rendimento_full_to_full · linha 558-559

A query SQL soma litros com data_transacao > anterior AND odometro <= atual. Depois, o código adiciona manualmente litros_abastecidos_atual novamente. Se o INSERT do abastecimento atual já estiver no banco (o método é chamado depois do INSERT), os litros serão contados duas vezes na soma do intervalo.

RISCOFaturamento parcial do turno ativo somado no fat_bruto do Raio-X mensal
profile_service.py · linha 75-86

A query de acumulado mensal soma todas as transações do mês, incluindo as do turno ainda aberto. Isso significa que o motorista vê o faturamento do turno em andamento misturado ao histórico fechado, gerando uma projeção dupla ao fechar o turno depois.

RISCOCache de perfil do motorista nunca invalidado após atualizar contrato
orchestrator_service.py · linha 903-910

O comando atualizar contrato faz UPDATE no banco mas não chama RedisFSMService.limpar_buffer(f"profile:{tenant_id}"). O próximo perfil retornará os dados de contrato stale do cache por até 1h.

RISCOkm_pessoal_intra não inclui o gap do abastecimento durante a pausa sem km registrado
turno_service.py · linha 392-402

Se o motorista pausar sem km, abastecer durante a pausa, e retomar sem km, o gap de uso pessoal intra-turno fica zerado. O cofre virtual será debitado na retomada (se km fornecido), mas km_pessoal_intra na agregação de pausas ficará zerado mesmo assim porque depende de km_fim - km_inicio. Não é um bug de conta — é uma limitação documentada — mas pode gerar surpresa no DRE.

🟡 Melhorias Menores / Inconsistências

MENORLabel "Projeção ao ritmo da meta" é enganoso quando usa media_fat_dia
orchestrator_service.py · linha 314

Após a correção que trocou meta_diaria por media_fat_dia, o texto ficou "Projeção ao ritmo da meta". Deveria ser "Projeção ao ritmo atual (média histórica)".

MENORamanha_dia = hoje_dia + 1 quebra no último dia do mês
orchestrator_service.py · linha 330

No dia 31, amanha_dia = 32, que nunca casa com dia_vencimento (1–31). Despesas que vencem no dia 1 do próximo mês não terão o aviso "vence amanhã" no dia 31. Correção: usar (hoje + timedelta(1)).day.

MENORMesmo problema de fim de mês existe no _listar_despesas_fixas
parametros_service.py · linha 668

" ⏰ _vence amanhã_" if dia_venc == hoje_dia + 1 else "" — idêntico ao bug anterior.

MENORCálculo de dias_uteis_restantes usa divisão linear simples (não calendário real)
orchestrator_service.py e profile_service.py · linhas 302 e 194

round(dias_uteis * (1 - hoje.day / 30)) assume todos os meses com 30 dias e não distingue fins de semana. Em fevereiro (28 dias) ou no dia 31 de janeiro, o cálculo fica errado. Para um app de finanças pessoais isso é aceitável, mas deveria ser documentado como estimativa.

MENORAbastecimento fast-path ignora comb_detectado já no estado ABASTECIMENTO_PRECO com valor embutido
orchestrator_service.py · linha 1583-1593

Quando o motorista manda "abasteci 150 gasolina" (sem preço), o sistema entra no estado ABASTECIMENTO_PRECO com comb:gasolina corretamente. Porém, quando a mensagem tem valor mas não tem preço e não detecta combustível, comb_abt fica vazio — e se o próximo estado detectar combustível no texto do preço, o params.get("comb") ficará errado.

MENORtotal_unidades_queimadas não soma GNV (total_unidades_queimadas_gnv nunca entra)
turno_service.py · linha 675

total_unidades_queimadas = total_unidades_queimadas_liq + total_unidades_queimadas_ele — o GNV não é incluído. Para veículos GNV puros, km_por_unidade sempre será 0, gerando "Rendimento: 0,00 km/L" no DRE.

MENORFallback de aluguel hardcoded como "Localiza Zarp" em vários pontos
turno_service.py · linha 835 e orchestrator_service.py · várias linhas

O fallback turno["locadora"] or "Localiza Zarp" pode confundir motoristas que trabalham com outras locadoras ou são proprietários. Deveria ser um genérico como "Contrato Padrão".

MENORO is_hibrido na Fase 4 fallback de _processar_uso_pessoal usa R$ 0,48/km (combustão), correto para o motor a combustão do híbrido, mas pode ser enganoso se bateria estivesse carregada
turno_service.py · linha 122-125

Quando há fallback (sem estoque e sem abastecimento), veículos híbridos usam R$ 0,48/km. Se o híbrido teve uso elétrico, o fallback é impreciso. Baixa severidade por ser Fase 4 (rara).

MENORMensagem de catch-all para !retirar caixa <nome> nunca é alcançada
parametros_service.py · linha 415

O regex match_excluir (linha 409) usa r"^!excluir\s+caixa\s+(\S.*)$" e o regex match_retirar_sem_valor usa r"^!retirar\s+caixa\s+(\S.*)$". Como o match_excluir vem antes e usa \S.*, ele nunca conflita — mas a ordem do processamento está correta. Porém, se o motorista escreve !retirar caixa Amortização de IPVA/Seguro (com espaço no nome), o match_retirar com valor falha (sem número ao final) e o match_retirar_sem_valor captura o nome com espaços corretamente. Isso é o comportamento que disparou a mensagem do usuário no início da conversa — e está correto.
